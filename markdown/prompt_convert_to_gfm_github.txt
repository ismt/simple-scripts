Преобразуй прикреплённый/вставленный документ в формат GitHub 
Flavored Markdown (GFM), полноценно используя все возможности, 
которые поддерживает GitHub.

Что нужно сделать:
- Сохрани всю структуру, смысл и содержание документа без потерь — 
  не сокращай, не перефразируй текст, меняй только разметку.
- Замени конструкции других диалектов на GitHub-эквиваленты, если 
  это уместно по смыслу:
  - {#custom-id} у заголовков → убери, используй автогенерируемый 
    якорь GitHub. Если id мог использоваться во внешних ссылках, 
    вставь перед заголовком <a id="старый-id"></a>, чтобы они 
    не сломались. GitHub добавит к id префикс user-content-, но
    ссылка вида #старый-id всё равно сработает
  - блоки-предупреждения из MkDocs/Pandoc/Docusaurus (::: note, 
    admonitions, кастомные блоки) → замени на alert-блоки GitHub:
    > [!NOTE], > [!TIP], > [!IMPORTANT], > [!WARNING], > [!CAUTION]
  - обычные списки задач без чекбоксов → преобразуй в - [ ] / - [x], 
    если по смыслу это чек-лист
  - HTML-таблицы → переводи в таблицы через | ТОЛЬКО если в них нет 
    rowspan/colspan и нет блочного содержимого в ячейках (списков, 
    абзацев, блоков кода). GFM-таблица такого не умеет, перевод был 
    бы потерей данных. Таблицы с объединениями или блочным 
    содержимым оставляй HTML — GitHub его рендерит
  - жёсткий перенос через два пробела в конце строки → замени на 
    <br> (два пробела невидимы и вырезаются редакторами)
- Таблицы: выравнивание задавай явно — --- (по умолчанию, слева), 
  :--- (слева), :---: (по центру), ---: (справа). Сохрани то 
  выравнивание, что было в оригинале.
- Где уместно, добавь:
  - зачёркивание ~~текст~~ для устаревших пунктов
  - <details><summary>...</summary>...</details> для длинных 
    вспомогательных блоков (логи, примеры, второстепенные детали)
  - бейджи через ![alt](url), если в документе есть статусы 
    (версия, лицензия, сборка) — только если такие данные есть 
    в исходном документе, не выдумывай
- ASCII-арт и текстовые схемы НЕ переписывай в ```mermaid по 
  умолчанию: восстановление связей по картинке — это домысливание, 
  а не смена разметки. Если mermaid-версия явно полезнее, добавь 
  её рядом, а оригинал сохрани в <details>, ничего не удаляя.
- НЕ добавляй @упоминания и #123-автоссылки на issues/PR, если их 
  не было в исходном документе — не выдумывай несуществующие ссылки.
- Код оформи тройными обратными кавычками с указанием языка.
- Проверь и поправь все внутренние ссылки на заголовки под 
  сгенерированные GitHub id. Правило: нижний регистр, пробелы 
  заменены на дефисы, пунктуация убрана, дефисы и подчёркивания 
  сохранены, кириллица сохранена, эмодзи вырезаны. Одинаковые 
  заголовки получают суффиксы -1, -2 в порядке следования — учти 
  это, если в документе есть повторяющиеся заголовки.

Учитывай, что итоговый документ будет открываться на GitHub 
(README, PR, issue, wiki) — GitHub-специфичные фичи использовать 
можно и нужно, если они делают документ понятнее.

Верни готовый документ целиком в одном блоке кода, огороженном 
ЧЕТЫРЬМЯ обратными кавычками с пометкой markdown (````markdown), 
чтобы тройные кавычки внутри документа не разорвали блок (если 
в документе уже есть блок из четырёх кавычек — возьми пять). 
Пояснения — только после блока, если они действительно нужны.
